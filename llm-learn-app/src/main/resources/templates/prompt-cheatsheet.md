## 一、Prompt 设计原则（黄金三律）

| 原则 | 说明 | 反例 → 正例 |
|------|------|-------------|
| **清晰** | 指令无歧义，目标明确 | "写个东西" → "写一篇500字的产品介绍" |
| **具体** | 给约束条件（格式、长度、风格） | "解释一下" → "用初中生能理解的语言解释，不超过200字" |
| **结构化** | 分步骤、分层级，用分隔符 | 一坨文字 → 用 `###` 分节、用 `---` 分隔 |

## 二、八大核心技术

### 2.1 Zero-shot（零样本）

**定义**：不给示例，直接提问

**适用场景**：
- 通用任务（翻译、总结、改写）
- 模型本身已具备的能力

**模板**：
```
请[动词][任务描述]

约束条件：
- [约束1]
- [约束2]

输出格式：[格式要求]
```

**示例**：
```
请将以下英文翻译成中文：

原文：{text}

约束：
- 保持专业术语不翻译
- 语言简洁正式

输出格式：直接输出译文，无需解释
```

---

### 2.2 Few-shot（少样本示例）

**定义**：给几个示例，让模型模仿

**适用场景**：
- 特定格式输出（JSON、代码风格）
- 颀域任务（医疗、法律）
- 模型容易理解偏差的任务

**模板**：
```
任务：[任务描述]

示例：
输入：{example1_input}
输出：{example1_output}

输入：{example2_input}
输出：{example2_output}

现在请处理：
输入：{actual_input}
输出：
```

**示例数量建议**：
| 任务复杂度 | 示例数量 |
|------------|----------|
| 简单格式 | 1-2个 |
| 中等复杂 | 3-5个 |
| 高复杂度 | 5-8个（但消耗Token多） |

**关键技巧**：
- 示例质量 > 示例数量
- 示例要覆盖边界 case
- 输入输出格式一致

---

### 2.3 Chain-of-Thought（思维链）

**定义**：引导模型逐步推理，展示思考过程

**适用场景**：
- 数学计算、逻辑推理
- 复杂问题分解
- 需要"解释原因"的任务

**触发方式**：

| 方式 | Prompt写法 | 效果 |
|------|------------|------|
| **显式引导** | "请一步步思考" | 最稳定 |
| **示例引导** | 给一个带推理过程的示例 | 效果更好 |
| **Zero-shot CoT** | "Let's think step by step" | 简单任务够用 |

**模板（显式）**：
```
任务：[复杂任务]

请按以下步骤思考：
1. 先分析问题的核心是什么
2. 列出需要考虑的因素
3. 逐步推导答案
4. 最后给出结论

请展示完整的思考过程，然后给出最终答案。
```

**模板（示例引导）**：
```
任务：数学推理

示例：
问题：小明有5个苹果，给了小红2个，又买了3个，现在有多少个？
思考过程：
1. 初始：5个苹果
2. 给小红2个：5 - 2 = 3个
3. 买了3个：3 + 3 = 6个
4. 最终答案：6个苹果
答案：6

现在请处理：
问题：{actual_question}
思考过程：
```

### 2.4 Role Prompting（角色设定）

**定义**：用 System Prompt 设定角色身份

**适用场景**：
- 专业领域（医生、律师、程序员）
- 特定风格（幽默、严肃、口语化）
- 用户个性化定制

**角色要素**：
| 要素 | 说明 | 示例 |
|------|------|------|
| **身份** | 职业角色 | "你是一名资深Java架构师" |
| **经验** | 专业程度 | "有15年企业级开发经验" |
| **风格** | 输出风格 | "回答简洁、代码优先" |
| **约束** | 行为限制 | "不解释概念，直接给解决方案" |

**模板**：
```
System Prompt：
你是一名[角色身份]，[经验描述]。

你的特点：
- [特点1]
- [特点2]

回答风格：
- [风格要求]

回答约束：
- [约束1]
- [约束2]

---

User Prompt：
{用户问题}
```

**示例（Java架构师）**：
```
System：
你是一名资深Java架构师，有15年企业级开发经验。

特点：
- 擅长Spring Boot微服务架构
- 对性能优化有深入研究
- 代码风格：简洁、注释精准

风格：
- 先给代码，再解释关键点
- 用表格对比方案优劣
- 不说废话，直击问题

约束：
- 不解释基础概念（如"什么是IoC"）
- 代码必须可运行
- 每次回答不超过300字

---

User：
帮我设计一个高并发订单系统架构
```

### 2.5 Self-Consistency（自一致性）

**定义**：多次采样，取共识答案

**适用场景**：
- 答案不确定的任务
- 需要高准确率的场景
- 数学推理、选择题

**实现方式**：
1. 同一 Prompt 调用 LLM 多次（temperature > 0）
2. 收集所有答案
3. 取出现次数最多的答案（投票）

**成本提示**：会消耗更多 Token，谨慎使用

---

### 2.6 Tree-of-Thought（思维树，ToT）

**定义**：让模型生成多个思考分支，探索不同路径，选择最优解

**核心思想**：
- CoT 是单路径推理（一条线走到底）
- ToT 是多路径探索（生成多个候选方案 → 评估 → 选择最优）

**适用场景**：
- 复杂决策问题（多方案对比）
- 创意生成（多角度构思）
- 战略规划（多条路径分析）
- 游戏/谜题（需要回溯的场景）

**实现流程**：
```
1. 生成阶段：让模型生成 N 个思考分支
2. 评估阶段：模型自我评估每个分支的质量
3. 选择阶段：保留最优分支，继续探索
4. 回溯机制：如果路径不好，可以回退探索其他分支
```

**模板（简化版）**：
```
任务：[复杂决策问题]

请按以下方式思考：

第一步：生成3个不同的解决思路
思路1：[方向1] → 可能的方案
思路2：[方向2] → 可能的方案
思路3：[方向3] → 可能的方案

第二步：评估每个思路
- 思路1的优点：... 缺点：...
- 思路2的优点：... 缺点：...
- 思路3的优点：... 缺点：...

第三步：选择最优思路，并详细展开
最终方案：...
```

**模板（完整版 - 多轮交互）**：
```
=== 第1轮：生成候选 ===
任务：[问题描述]

请生成3个不同的思考方向，每个方向给出初步方案（各不超过50字）。

=== 第2轮：评估 ===
候选方案：
- 方案A：[...]
- 方案B：[...]
- 方案C：[...]

请评估每个方案的：
1. 可行性（1-5分）
2. 成本（1-5分）
3. 风险（1-5分）
并给出综合评分。

=== 第3轮：选择并深化 ===
根据评估结果，选择最优方案（方案X），并详细展开实施步骤。
```

**与 CoT 的对比**：
| 维度 | CoT（思维链） | ToT（思维树） |
|------|--------------|--------------|
| **路径** | 单路径推理 | 多路径探索 |
| **成本** | 较低 | 较高（多次调用） |
| **适用** | 确定性推理 | 不确定性决策 |
| **回溯** | 不支持 | 支持 |
| **复杂度** | 中等 | 高 |

**成本提示**：
- 需要 3-5 轮 LLM 调用
- 适合高价值决策场景
- 不适合简单任务

### 2.7 Self-Reflection（反思机制）

**定义**：让模型检查自己的输出，发现错误并修正

**核心思想**：
- 第一轮：模型生成答案
- 第二轮：模型扮演"审查者"角色，检查答案
- 第三轮：如有问题，重新生成改进版

**适用场景**：
- 代码生成（检查语法、逻辑）
- 数学推理（验算答案）
- 专业内容（检查事实准确性）
- 高准确率要求的任务

**实现流程**：
```
1. Generate：模型生成初步答案
2. Critique：模型自我审查（扮演审查者角色）
   - 检查逻辑漏洞
   - 检查事实错误
   - 检查格式问题
3. Refine：根据审查结果，改进答案
```

**模板（两轮式）**：
```
=== 第1轮：生成 ===
任务：[任务描述]
请给出你的答案。

=== 第2轮：审查 ===
你刚才的回答是：
[模型的回答]

现在请扮演严格的审查者，检查这个回答：
1. 是否有逻辑错误？
2. 是否有事实错误？
3. 是否有遗漏点？
4. 格式是否符合要求？

如果有问题，请指出具体问题并给出改进建议。

=== 第3轮：改进 ===
根据审查结果，重新生成改进后的答案。
```

**模板（单轮式 - 更简洁）**：
```
任务：[任务描述]

请按以下步骤处理：
1. 先给出初步答案
2. 然后扮演审查者，检查自己的答案是否正确
3. 如果发现问题，指出并修正
4. 给出最终答案

输出格式：
### 初步答案
[...]

### 审查意见
[...]

### 最终答案
[...]
```

**示例（代码生成）**：
```
任务：用Java写一个单例模式的实现

请按以下流程处理：

1. 先写出代码实现
2. 扮演代码审查者，检查：
   - 是否有线程安全问题？
   - 是否有性能问题？
   - 是否符合单例模式规范？
3. 如果有问题，修正代码
4. 输出最终版本

输出格式：
### 初步代码
```java
...
```

### 审查意见
- 问题1：...
- 问题2：...

### 最终代码
```java
...
```
```

**与 Self-Consistency 的对比**：
| 维度 | Self-Consistency | Self-Reflection |
|------|------------------|------------------|
| **机制** | 多次生成 + 投票 | 生成 + 审查 + 改进 |
| **调用次数** | N次并行 | 2-3次串行 |
| **适用场景** | 不确定答案 | 答案需要验证 |
| **成本** | 较高 | 中等 |
| **效果** | 提高准确率 | 提高质量 + 发现错误 |

**成本提示**：
- 需要 2-3 轮 LLM 调用
- 适合代码生成、专业内容
- 可以结合 Role Prompting（审查者角色）

### 2.8 Prompt 模板管理

**定义**：将 Prompt 模板化，版本化管理

**核心要素**：
```
PromptTemplate {
id: "code-comment-generator-v1"
name: "代码注释生成器"
category: "code"
variables: ["code", "language"]
template: "...",
version: "1.0"
metadata: {
author: "空少"
created: "2026-04-30"
avg_tokens: 150
}
}
```

**Java实现（设计模式）**：
```java
public class PromptTemplate {
    private String id;
    private String template;
    private Map<String, String> variables;
    
    public String render(Map<String, String> params) {
        String result = template;
        for (Map.Entry<String, String> entry : params.entrySet()) {
            result = result.replace("${" + entry.getKey() + "}", entry.getValue());
        }
        return result;
    }
}

public class PromptTemplateManager {
    private Map<String, PromptTemplate> templates = new HashMap<>();
    
    public PromptTemplate get(String id) {
        return templates.get(id);
    }
    
    public void register(PromptTemplate template) {
        templates.put(template.getId(), template);
    }
}
```

## 三、场景选择指南

| 场景 | 推荐技术 | 原因 |
|------|----------|------|
| 通用翻译/总结 | Zero-shot | 模型已具备能力 |
| 特定格式输出 | Few-shot | 示例引导格式 |
| 数学/逻辑推理 | CoT | 展示推理过程提高准确率 |
| 专业领域咨询 | Role Prompting | 角色设定注入专业知识 |
| 不确定答案 | Self-Consistency | 多次采样取共识 |
| 复杂决策/多方案对比 | **Tree-of-Thought** | 多路径探索 + 评估最优 |
| 代码生成/高准确率任务 | **Self-Reflection** | 生成 + 审查 + 改进 |
| 批量任务 | 模板管理 | 提高效率、版本控制 |

## 四、常见错误速查

| 错误 | 表现 | 修正 |
|------|------|------|
| **指令模糊** | 输出偏离预期 | 加约束条件（格式、长度、风格） |
| **示例不一致** | 模型学习混乱 | 示例格式统一、质量高 |
| **角色设定太宽** | 回答泛泛 | 具体化经验、风格、约束 |
| **忽略Token成本** | 费用超标 | Few-shot控制在3-5个、精简Prompt |
| **没有版本管理** | 改了不知道哪版好用 | 用模板管理系统、记录版本效果 |

---

## 五、成本优化技巧

| 技巧 | 方法 | 节省量 |
|------|------|--------|
| **精简Prompt** | 去掉废话、用符号代替描述 | -30%~50% |
| **Few-shot限量** | 最多5个示例 | -40%~70% |
| **模板复用** | 相同任务用同一模板 | 避免重复设计成本 |
| **输出限制** | "不超过X字" | 控制输出Token |
| **缓存结果** | 相同请求缓存 | 零成本 |
